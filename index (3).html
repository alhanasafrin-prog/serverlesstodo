1. PROBLEM STATEMENT

Develop a basic To-Do application using serverless cloud services. The application should allow users to add, update, and delete tasks, mark tasks as completed, and store task information using a cloud service. The system must provide a responsive user interface and implement a complete serverless architecture leveraging Oracle Cloud Infrastructure (OCI) services.

Key Requirements:

  • Add tasks with descriptions
  • View all tasks with filtering options
  • Update/Edit existing tasks
  • Delete tasks
  • Mark tasks as completed
  • Store data in cloud database
  • Provide responsive and intuitive UI

2. PROJECT OVERVIEW

The Serverless To-Do Application is a modern web-based task management system built on serverless architecture principles. This project demonstrates the implementation of a complete cloud-native application using Oracle Cloud Infrastructure services without managing traditional servers.

The application provides users with a seamless experience to manage their daily tasks efficiently. All data is persisted in OCI NoSQL Database, ensuring scalability, reliability, and automatic backups. The architecture follows best practices for serverless computing, ensuring cost-efficiency and optimal performance.

4. PROPOSED SOLUTION

The proposed solution implements a complete serverless architecture where:

  • The front-end web application (HTML, CSS, JavaScript) is hosted on OCI Object Storage
  • All user requests are routed through OCI API Gateway
  • OCI Functions process business logic without server management
  • OCI NoSQL Database provides scalable, high-performance data storage

Architecture Flow:

User Browser → Web Application (OCI Object Storage) → API Gateway → OCI Functions → OCI NoSQL Database

8. APPLICATION WORKFLOW

Step 1: User Access

  • User opens the application in web browser
  • Application files are served from OCI Object Storage

Step 2: Add Task

  • User enters task description and clicks 'Add Task'
  • Request is sent through OCI API Gateway
  • OCI Function processes the request and validates data
  • Task is stored in OCI NoSQL Database
  • Response is returned to UI for display

Step 3: View/Filter Tasks

  • User can view all tasks or filter by status
  • OCI Function retrieves data from NoSQL Database
  • Tasks are displayed with real-time statistics

Step 4: Update/Delete Tasks

  • User can edit task descriptions or mark as completed
  • Changes are persisted to OCI NoSQL Database
  • UI updates immediately with new data

9. MAIN MODULES

Module 1: User Interface Layer (HTML/CSS/JavaScript)

Responsible for presenting the application to users and handling user interactions. Features include responsive design, real-time statistics, and task filtering.

Module 2: API Gateway (OCI)

Routes all requests to appropriate OCI Functions. Handles authentication, rate limiting, and request validation.

Module 3: Serverless Functions (OCI Functions)

Executes business logic for task operations (create, read, update, delete). Each function handles a specific operation.

Module 4: Database Layer (OCI NoSQL Database)

Stores and retrieves task data. Provides ACID guarantees and automatic indexing for efficient queries.

11. IMPLEMENTATION DETAILS

Frontend Implementation:

The frontend is implemented using vanilla JavaScript with no external dependencies for maximum portability. Key implementations include:

  • Responsive CSS Grid and Flexbox layouts
  • Event-driven architecture for user interactions
  • DOM manipulation for dynamic content rendering
  • Local storage simulation for cloud data sync

Cloud Service Implementation:

OCI Object Storage hosts static assets (HTML, CSS, JavaScript files). OCI API Gateway provides RESTful endpoints for CRUD operations. OCI Functions execute business logic, and OCI NoSQL Database stores all task data.

12. CLOUD DATA STORAGE

Database Schema:

The OCI NoSQL Database stores tasks with the following structure:

Task Collection:

  • id (Primary Key): Unique task identifier (timestamp-based)
  • text (String): Task description
  • completed (Boolean): Task completion status
  • createdAt (Timestamp): Task creation date and time
  • updatedAt (Timestamp): Last modification date and time

Data Persistence:

  • All data modifications trigger immediate cloud sync
  • Automatic backups and replication
  • ACID compliance for data consistency

Data Security:

  • Encryption at rest and in transit
  • Access control via OCI Identity and Access Management
  • Audit logging for compliance

13. API & FUNCTION DETAILS

RESTful API Endpoints (via OCI API Gateway):

POST /tasks - Create new task

GET /tasks - Retrieve all tasks

GET /tasks/{id} - Retrieve specific task

PUT /tasks/{id} - Update task

DELETE /tasks/{id} - Delete task

OCI Functions:

Each endpoint maps to an OCI Function that handles the business logic. Functions are triggered automatically by the API Gateway based on the request path and method.

17. ADVANTAGES

Serverless Architecture Benefits:

1. No Infrastructure Management

  • Eliminates the need to manage servers
  • OCI handles all operational concerns

2. Cost Efficiency

  • Pay only for actual resource consumption
  • Zero cost for idle resources

3. Automatic Scalability

  • Automatically scales to handle traffic spikes
  • No manual capacity planning needed

4. High Availability

  • Built-in redundancy across multiple zones
  • Automatic failover and recovery

5. Faster Development

  • Focus on application logic instead of infrastructure
  • Rapid deployment and updates

6. Integrated Monitoring

  • Built-in logging and monitoring
  • Easy debugging and troubleshooting

18. LIMITATIONS

Current Implementation Limitations:

1. Cold Start Latency

  • First invocation of functions may have slight delay
  • Mitigated by using provisioned concurrency

2. No User Authentication

  • Current version uses shared storage for all users
  • Future version will implement OAuth 2.0

3. Limited Data Validation

  • Basic validation implemented on frontend
  • Can be enhanced with server-side validation

4. Vendor Lock-in

  • Tightly integrated with OCI services
  • Migration to other providers requires refactoring
